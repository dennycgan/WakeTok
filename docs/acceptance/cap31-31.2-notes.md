## Case A — single asset: first visit freezes, revisit stays still

Owner report: first auto-play freezes on the last motion frame (~4.33 s,
Share dim), then still + Share enabled; revisit shows still only; leaving
mid-play keeps revisit auto-play; long-press replay "works"; other Live
Photos from the same day are fine; Photos app fine; competitor fine.

### Probe findings

| Signal | Case A (IMG_1935) | Same-day controls |
|--------|-------------------|-------------------|
| PhotoKit `requestLivePhoto` callbacks | 1 (not degraded) | 1 (not degraded) |
| `willBeginPlaybackWith` after `startPlayback` | ~38 ms | 34–61 ms |
| `didEndPlaybackWith` | **never** (auto-play and long-press) | 1616–2475 ms after start |
| `stopPlayback()` fires `didEnd` | not observed in WakeTok (view unmounted within ms); not tested in the native repro | not synchronously; asynchronously ~305–312 ms later (native repro, IMG_1934); not observed in WakeTok (view unmounted within ms) |
| `livePhoto = nil` fires `didEnd` | yes, mid-motion (sync, 3 cases in acceptance) | yes (sync) |
| Dart ended watchdog | fired 6.001 s after arm → skip-set add | never |
| Revisit | `LIVE_SKIP_WATCHDOG_ID` → still | auto-play |

### 4.33 s derivation

Watchdog is armed just before `startPlayback` and fires at 6.001 s.
`willBegin` arrives ~0.038 s after issue; the video track is 1.683 s, so
the last frame is on screen from ~1.72 s:

6.001 − 0.038 − 1.683 ≈ **4.28 s** frozen, against the owner's hand-timed
4.33 s.

### Symptoms → mechanism

1. **Freeze on last frame, Share dim ~4.3 s, then still + Share enabled.**
   `didEnd` never arrives, so `liveMotionMounted` stays true until the 6 s
   watchdog unloads the surface. Share enable requires Live motion idle —
   **ADR-051 D14** `¬liveMotionMounted` (not ADR-054, which is the
   cover-visible gate).
2. **Revisit stays still.** The watchdog timeout adds the id to the
   Session skip set (`browseLiveMotionWatchdogSkipIdsProvider`); revisit
   consults it and does not arm Live.
3. **Leaving mid-play keeps revisit auto-play.** Leave-current tears down
   and cancels the watchdog before it fires, so the id never enters the
   skip set.
4. **Long-press replay looks normal.** Release-to-stop hard-cuts and hides
   the missing `didEnd`; a full hold past the natural end runs to the 6 s
   watchdog as well.

### Debt / ADR mapping

- Debt **470** (magnified Live long-press does not replay): no — fit
  scale, replay path is not involved in the root cause.
- Debt **471** (album 213 membership vs `.photoLive` identity): no — the
  asset is `.photoLive`, `playbackStyle = .livePhoto`, and Live chrome /
  request behave normally.
- **ADR-051 D12** (share = still key frame): no — Share content is not
  wrong; only its enable timing follows the stuck motion state (D14).

→ **New path:** motion end depended solely on a system callback that is
not guaranteed.

The −0.371 s sample: `didEnd` arrived 14 ms after the page changed to
IMG_1935, before `LEAVE_CURRENT` and before any Dart cancel, and Dart
never logged `LIVE_ENDED_RX`. The view leaving the visible page ends
playback early; it is not a natural end.

### Sampling hygiene (slack data)

A sample counts only when all hold: Host forwarded a **system** end for
the current, un-invalidated play (`LH_END_SYSTEM`); the view was still in
its window (`window=true`); Dart logged `LIVE_ENDED_RX` while the page was
current. Each sample is tagged by `LIVE_PLAY_ISSUE` `path` = `auto` /
`replayR` / `replayS`. Overrun = end − `willBegin` − movie duration.

Slack rule: slack = max overrun + ≥ 0.25 s, capped at 1.0 s; if Kafka max
> 0.55 s use 1.0 s; if any device max > 0.75 s stop and re-discuss.

### Fix (ADR-063, Accepted 2026-09-28; work `b8b7b9b`)

Host motion-end fallback for unedited `.livePhoto`-style assets: after
ready, one network-off streaming read of paired-video `moov/mvhd`
(no file copy; request cancelled right after `mvhd`); deadline =
`willBegin` + duration + slack; on timeout stop + emit the same ended
event. Host forwards only the first end of the current play on the
current surface. Dart watchdog / skip set unchanged (last resort). Pigeon
signature unchanged (doc comment only).

### Slack decision

The stop rule fired (i17 max 756 ms > 0.75 s). The rule's value
(756 + 250 = 1006 ms) exceeds the 1.0 s cap. After discussion the owner
chose **1.0 s** (`LiveMotionEndPolicy.slack`): margin ~244 ms over the
largest observed overrun, slightly below the rule's 250 ms — an
owner-accepted value, not a full match of the rule.

### Native repro (minimal standalone UIKit app, i17, iOS 26.6.2)

- IMG_1935 natural end: no `didEndPlaybackWith` in 10 of 10 runs
  (default `playbackGestureRecognizer` 0/5, disabled 0/5).
- Control IMG_1934: `didEnd` delivered in 10 of 10 runs.
- `stopPlayback()` on IMG_1934 (0.5 s after `willBegin`, view kept in
  the window, observed 2 s): `didEnd` not synchronous; delivered
  asynchronously ~305–312 ms later. WakeTok did not observe it after a
  stop (21 cases, no callback for 0.43–4.7 s) most likely because the
  Dart side unmounts the view within 0–14 ms of the stop (view release
  time is not logged).
- Conclusion: treated as iOS / PhotoKit behavior specific to this
  asset's content, not triggered by WakeTok's Platform View hosting or
  gesture configuration; the repro cannot rule out additional effects
  specific to Platform View hosting.

## Case B — fixed condition: Live Photos shot of a computer screen

Owner report: Live Photos shot of a computer screen showing game
cutscenes (iPhone 17 main camera, 26 mm f1.6, 24 MP 5712×4284 HEIF,
~5.1 MB, STANDARD). Every photo in the set shows the problem:
(1) the WakeTok still shows moiré stripes; Photos and a competitor do
not; the stripes disappear from the first motion frame; (2) sharing to
a third-party extension (WhatsApp / WeChat / Facebook / QQ) opens the
extension, which dismisses itself after ~1 s; AirDrop and Notes work;
ordinary photos share normally; (3) Live playback, revisit and
long-press are normal. 24 MP, HEIF and Live are shared by ordinary
photos and are not distinguishing features.

Owner scope (2026-09-29): no diagnosis engineering (no control groups,
jetsam / Analytics hunting, Console capture or A/B probe builds). Split:
31.2b-2 share first, then 31.2b-1 moiré.

### 31.2b-2 — share

- Evidence accepted by the owner: Share was enabled in the screenshot,
  so the displayed layer was Layer 2 (ADR-051 D14); the same photo
  shared from the Photos app, which hands over the original file, works.
- Recorded cause: sharing failed when handing over a full-size decoded
  image and works when handing over the original file. The decoded
  size (5712 × 4284 × 4 ≈ 98 MB) is not claimed as the proven cause:
  ordinary 24 MP photos have the same decoded size and share normally.
- Fix (ADR-064, work `bd6a870`): current-version image data
  (`requestImageDataAndOrientation`, `.highQualityFormat`) with GPS
  removed, handed over as a file under `tmp/share/<uuid>/`; lossless
  metadata rewrite verified by re-read, JPEG 0.9 re-encode as fallback,
  share fails if both fail. Video share unchanged.
- Mac feasibility (macOS 26.6.1, throwaway script under `tmp/`, not
  committed; three real iPhone HEICs incl. one edited render, plus
  JPEG copies with orientation 6):

| Variant | HEIC | JPEG |
|---------|------|------|
| `kCGImageMetadataShouldExcludeGPS` only | returns true, **GPS kept** (output byte-identical) | GPS removed, **orientation / date / model dropped** |
| source metadata + merge + exclude GPS | GPS removed; orientation, date, model, HDR gain map kept; decoded pixels identical | GPS removed; orientation 6, date, model kept; pixels identical |
| JPEG re-encode (0.9), GPS removed | GPS removed; orientation, date, model kept; HDR gain map lost; 1.5–1.8× larger | — |
