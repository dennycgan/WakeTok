# Cap 22.5 — Endless round boundary (scheme A)

## Goal

Doom-scroll across Shuffle round boundaries with a **known hard cut**: one
static placeholder page after the last real item, then
`advanceToNextRound` + `roundEpoch` remount + `jumpToPage(0)`. Does **not**
promise continuous scroll momentum across the round boundary.

## Contract (scheme A — current)

1. **Placeholder:** When session queue length `n > 1`, PageView
   `itemCount = n + 1` for the whole round (no dynamic insert at n-2/n-1).
   Index `n` is a **forged** waiting page
   (`mainBrowseEndlessRoundPlaceholder`) — center
   `mainBrowseFeedLayer1Loading` ("Loading item") on `feedBackground`
   only. **Not** a `MediaFeedPage`, not interactive, and **no** corner
   gold spinner (a real spinner on a fake page reads as live work /
   Cap 15–17 “gold peek on black”).
2. **Trigger:** `onPageChanged` to the placeholder **arms** only (does not
   `setIndex` to the placeholder). Advance runs on true
   [`ScrollEndNotification`] while [`verticalFeedPageSettled`] holds for
   index `n` — then atomically `advanceToNextRound` + `setIndex(0)` +
   remount + `jumpToPage(0)`.
3. **Overscroll fallback:** [`isEndlessRoundAdvanceScroll`] (true trailing
   overscroll) calls the same advance helper (`_advancingRound` latch).
4. **No back-scroll** into the previous round after advance (new queue +
   remount).
5. **Toast:** `mainBrowseNewRoundToast` via `showCap19BrowseToast` after
   jump lands on the new-round head (EN/ZH strings live only in
   `lib/l10n/app_en.arb` and `lib/l10n/app_zh_Hans.arb`). Settings
   **Browse notices** toggle (default ON). Dismiss when leaving feedIndex 0
   or leave Browse.
6. **Cap19 × remount:** clear `cap19LeftSwipeDragProvider` before remount;
   gesture `mounted` guards (debt **462** Closed).
7. **Landing chrome (B):** `delayInitialLayer1CenterLabel` (ADR-039) is
   keyed only on `BrowseChromeState.feedDataSourceId` change (All / Photos /
   Videos / pool origin). `advanceToNextRound` reshuffles + bumps
   `roundEpoch` on the **same** origin — it does **not** change
   `feedDataSourceId`, so the source-switch center-label delay is **not**
   armed on round remount. Verified in code review + `W-END-9`.
8. **No new ADR.**

## Explicit non-goals

- Zero hitch / continuous momentum across rounds (see retrospective).
- Real bridge pages / soft commit / controller align / dual epoch.
- Scheme D (monotonic infinite index space) — independent future Cap;
  seed notes below, not an approved implementation contract.

## Scheme D — future Cap seed (not in 22.5)

**Status:** sketch only. Listed in the first Cap 22.5 design pass, then
excluded as highest complexity. **Not** an ADR, **not** scheduled, **not**
a half-built path behind scheme A. Debt **463** names D as the only route
to a true zero floor; this section records what was said then and what Cap
22.5’s soak later proved must constrain any future D Cap.

### Original sketch (design pass)

**Heavier option: multi-page / whole-round append (true infinite list).**

Append the entire next Shuffle round into the **same** PageView so the
presentation index space grows monotonically (never resets to 0 via
`roundEpoch` remount + `jumpToPage(0)`).

| | |
|---|---|
| Pros | Closest to true endless / doom-scroll continuity across rounds |
| Cons | New contracts for `roundEpoch` / page keys, preheat window, back-scroll across rounds, memory, and identity — far beyond Cap 22.5 misc polish |

**Do not ship inside 22.5.** If pursued later: independent Cap + ADR.

### Why only D can drive the floor to zero

Cap 22.5 soak (soft-commit / real-bridge path) showed that under continuous
fast scroll, a discrete **data-source identity swap** (round N → N+1 under
the same scrollable) overlaps in-flight `DragScrollActivity` / Ballistic on
the common path (14/15 Drag at swap; 15/15 later Drag; 14/15 Ballistic). A
discrete swap cannot be guaranteed never to collide with continuous scroll.

Bridge pages, soft commit, dual epoch, and remount-delay tuning only lowered
**hit probability / cost when hit** (measurable L1/L0 wins). They never
removed the swap event. **While a swap event exists, the floor is not zero.**

Scheme D’s essential property is the opposite: the PageView’s scrollable
item identity space **does not swap** — it only **appends**. Presentation
indices keep increasing; domain must map a virtual feed index onto round /
local-queue coordinates without rebuilding the scrollable’s identity mid-
gesture.

### Open contracts a future D Cap must decide

These were named as disadvantages in the first pass and were **never**
product-resolved. A D Cap cannot treat them as implementation detail:

1. **Presentation vs session identity** — How `roundEpoch`, PageView /
   page `ValueKey`s, and `MediaFeedPage` State survive append without the
   Cap 13.4 / scheme A remount+jump pattern.
2. **Domain virtual mapping** — feedIndex → (round, localIndex) or
   equivalent; how `prepareNextRoundQueue` / Shuffle `first≠last` apply at
   each round seam inside one growing list; whether Consumption Session
   stays “one table per round” internally while UI sees a concatenated view.
3. **Preheat window** — current ±1 (and Cap 14.5 release) over a
   monotonically growing `itemCount`; eviction when the user is far past
   early rounds.
4. **Back-scroll across round boundaries** — product yes/no (never opened
   under scheme A: advance remounts and drops the prior round). If yes:
   how far, and what “previous round” means for Shuffle identity.
5. **Memory / identity** — when to drop trailing rounds from the PageView
   model without introducing a new swap hitch; Host / L1 seed / L2-ready
   token lifetimes across retained pages.
6. **Boundary UX** — whether toast / forged placeholder remain if the
   cross-round fling is truly continuous; scheme A’s “legible boundary
   marker” framing may not apply.

### Relationship to scheme A and debt 463

- **Scheme A** is the shipped, **Accepted (permanent)** product semantics for
  Cap 22.5: a user-legible round boundary (forged Loading-item placeholder +
  deliberate pause), not an unexplained hitch. It does **not** deliver
  zero-hitch endless continuity.
- **Debt 463** records the architectural floor under finite-round table +
  boundary swap, and points here for the full retrospective + this D seed.
- Reopening zero-hitch doom-scroll across rounds means **starting a D Cap**,
  not polishing scheme A further.

## Cap 22.5 — end-of-queue → next-round jump feel: root-cause retrospective

**Verdict: under “one finite table per round + a data-source identity swap
at the boundary,” this hitch cannot be optimized to zero. That is a
mathematical floor, not under-investment.**

Device soak under the cross-round soft-commit path (multi-run sampling)
showed that on continuous fast scroll, 14/15 samples had the PageView in
`DragScrollActivity` at the moment of the data swap; within the window,
15/15 saw a later Drag and 14/15 a Ballistic. That confirms the root cause:
as long as there exists a discrete instant that must retarget the scrollable’s
data-source identity from round N to round N+1, under sustained doom-scroll
that event will eventually overlap an in-flight drag or ballistic activity
and interrupt it. A discrete event cannot be guaranteed never to overlap a
continuous process — that is the nature of the two kinds of thing, not an
engineering shortfall.

The dozen-plus optimization rounds (real bridge pages / soft commit / dual
epoch / controller rebuild timing / delay cut from 50 ms to 10 ms) all aimed
at “lower the hit probability / lower the cost when hit,” and they did move
measurable needles (L1 path ~5 ms; L0 ~66 ms → ~41.5 ms). None of them asked
the upstream question — whether the swap event itself must exist — because
while that event exists, the floor is not zero.

The only design that can drive the floor to zero is a monotonically
increasing presentation index space that never swaps identity (scheme D:
true infinite list — see **Scheme D — future Cap seed** above). Scheme D
was correctly identified as highest complexity and needing its own Cap, so
it stayed out of 22.5. **What went wrong was excluding D without also saying
out loud that choosing scheme C (finite per-round table + boundary swap)
means deliberately accepting a non-zero floor** — so later debugging kept
chasing an impossible “maybe we can still get to zero,” burning many
implementation probes before device data forced the structural conclusion
that should have been locked at selection time.

**Lesson:** for “can we fully eliminate this UX defect?” questions, selection
must first ask whether any candidate can theoretically drive the defect to
zero; if one can but was rejected for complexity, the chosen path’s goal
must be renamed from “eliminate” to “compress probability/cost to an
accepted waterline,” and that downgraded goal must be written down and
agreed at selection — not carried as an unchecked “eliminate” expectation
into implementation detail until soak data rediscovers the structure.

**Disposition:** ship scheme A (static placeholder after the last item;
center Loading-item copy only, no corner gold spinner; non-interactive);
advance only after **ScrollEnd** settle on the placeholder, then
`advanceToNextRound` + `jumpToPage(0)` (irreversible remount must not fire
mid-page hesitation); keep `isEndlessRoundAdvanceScroll` as true
trailing-overscroll fallback. Accept the known cost: a hard cut, no
continuous momentum. True zero-feel cross-round work, if ever pursued, is
scheme D only — independent Cap (seed section above). Out of scope for 22.5
and any “misc polish” track.
