### Outward-caret overlap note

`Key('cap30CreatePoolTip')` is the **Material bubble only** (caret is a
sibling above the caret–bubble gap). Tests therefore:

- Assert **bubble** does not overlap Create / helper / Built-in / Saved.
- Assert **caret** does not overlap Create (+ Limited helper), and
  `arrow.top >= create.bottom` (via `_expectOutwardCaretAim` /
  `_expectCaretClearsAnchor`).

#### Caret vs Built-in / Saved — not in automation (manual)

**Decision:** Do **not** assert caret AABB vs Built-in or Saved.

**Classification (not “maybe someday”):** On EN@390 the caret **does**
AABB-intersect Saved (`arrow∩saved == true`). That is a **true geometry
intersection** of render boxes, **not** a latent miss. It is a
**product false positive** for “caret covers the Saved label”:

- Create stadium bottom ≈ **36**; Saved menu box bottom ≈ **42** (taller
  hit/layout box than the capsule).
- Saved box also extends **horizontally under** Create (Saved right ≈
  349 overlaps Create’s x-range).
- Caret sits in Create’s clearance band (≈ y **40–54**, aimed at Create
  center). Boxes cross; the caret is still under Create, not over the
  Saved title glyph.

Requiring `arrow∩Saved == false` would force tip clearance to absorb
unrelated menu padding — wrong coupling. Bubble overlap vs Saved remains
automated. **Caret-not-covering-Saved visually** is accepted as **manual**
coverage: on **M2** (narrow) eyeball that the outward caret does not sit
on the Saved pools label.

## Edge cases (accepted)

Layer 1 (“Loading item”) and `<1>` are **not** bound. Code audit for Cap
30.7 found **no hard gate / step-machine bug** from that decoupling.
Accepted edges:

1. **Center visual stack** — Feed paints Loading item under the Browse
   pane Stack; `<1>` Host sits above and is centered. Opaque coach often
   covers the Loading item label. Gesture still works (`IgnorePointer` on
   coach). Visual competition only.
2. **Slow Layer 1 / iCloud** — `<1>` 2s timer (and early page-change end)
   run independent of decode. Coach may finish and `<2>` may appear while
   the first (or next) item is still Loading item. Step index stays
   correct; timeline of tip vs pixels can diverge. Early page-change
   while L1 is still spinning is **by contract** (ADR-060: early end =
   PageView page change), not a defect.
3. **Layer 1 fail / error chrome** — If the current item fails to load
   but `assetId` remains, `<1>` still runs to completion (or early-ends
   on page change). First impression can sit on an **error / fail** page,
   not only on a busy spinner — distinct from (1) and worth revisiting in
   a later visual-polish Cap if desired.
4. **Mid-chain `browseItemReady` true→false** — **Supplement to Cap 30.2
   accepted risk** (see `cap30-30.2-notes.md`), not a new Cap 30.7 find.
   Mechanism: with `activeChrome` already `verticalHint`,
   `_maybeBeginStep` returns early when `!_browseItemReady` and does
   **not** cancel the in-flight chrome. Rare in practice.
5. **a11y** — Loading item semantics and coach may both be present.
   Deferred to a later accessibility Cap; **out of Cap 30**.
