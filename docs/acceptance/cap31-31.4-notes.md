owner proposed: verify "follow system" for Light/Dark and language
(verify-only, no product change); fix/polish because it is an existing

Scope: live Appearance switch while foreground on the surfaces that
follow the system (Settings pane incl. info bubbles, permission request /
blocked pages); language = Traditional Chinese, uncovered languages, and
per-app language. Out of scope by design: forced-dark Browse surfaces
(ADR-015 D7 / ADR-017: bottom bar, feed, top chrome, half-sheets, Build
Pool, Cap 30 coaches). **Verified 2026-09-28 (iPhone 17 simulator, iOS
26.3, Debug):**
- Appearance method: `xcrun simctl ui <sim> appearance light|dark`
  while the app is foreground. Settings pane, permission request page,
  and permission blocked page all follow the switch live (light → dark
  → light) with no restart; bottom bar stays dark (ADR-017). Minor: an
  info bubble left open during the switch keeps its old colors until
  reopened (colors are resolved when the bubble opens) — recorded only.
  Loading / error gate scaffolds are transient and were not captured.
- Language, **system-wide** setting (global `AppleLanguages` /
  `AppleLocale` written to the simulator's global domain, simulator
  rebooted, app domain has no override, cold launch without arguments):
  `[zh-Hans]` → zh_Hans (positive control); `[zh-Hant]` → zh_Hans;
  `[ja]` → en; `[ja, zh-Hans]` → en (first-preferred-only, kickoff ADR-U
  §10). No crash / blank page on any.
- Language, **launch argument** `-AppleLanguages (<lang>)` (argument
  domain; closer to a per-app override than a system change):
  `zh-Hant` → zh_Hans; `ja` / `ko` / `fr` → en.
- Language, **per-app override** emulation (`AppleLanguages` written to

owner proposed: make the iOS status bar readable on forced-dark
surfaces under Light Appearance; fix/polish because Browse shows dark
status bar icons on a black background (time / signal / Wi-Fi vanish),
so the forced-dark promise of ADR-015 D7 is broken at the status bar.
**Confirmed 2026-09-28 (simulator, Light):** (a) cold launch straight
into Browse → icons invisible; (b) permission page → Browse in one
session → icons invisible. Dark Appearance → icons visible. Style is
also sticky across surfaces: after Build Pool (dark AppBar) the light
icons stay, so Browse looks right but the Light Settings pane then shows
white icons on a light background. Root cause: no surface declares a
status bar style; `MaterialApp` sends a follow-theme default only when the
theme changes, and the last AppBar style persists across navigation.
**Design approved (owner 2026-09-28):** shell `AnnotatedRegion` — Browse
always light icons, Settings follows Appearance — plus an app-root
follow-theme baseline in `MaterialApp.builder`; guards
`W-31.4-statusbar-*`; surface table and future-surface rule in
`media-chrome-layout-notes.md` §15.

owner proposed: declare en + zh-Hans in `CFBundleLocalizations` /
`knownRegions` so iOS Settings shows a per-app Language row.
**Decided not to do: v1 language follows system only, no per-app
Language row (owner decision, 2026-09-28).** Evidence (iPhone 17
simulator, iOS 26.3, build = `e9765db` + the declaration, not committed):
- In-app result unchanged by the declaration: system `[zh-Hans]` /
  `[zh-Hant]` → zh_Hans; `[ja]` / `[ja, zh-Hans]` → en; launch argument
  `zh-Hant` / `zh-Hans` → zh_Hans, `ja` / `ko` / `fr` → en.
- The new Language row follows iOS's rule ("first supported language in
  Language & Region"), which is the opposite of kickoff ADR-U §10
  (first-preferred only) in two cases:
  - `[ja, zh-Hans]`: row shows Simplified Chinese (default, checked),
    app shows English. Tapping Simplified Chinese writes no override, so
    the app stays English — Chinese cannot be chosen from the row.
  - `[zh-Hant, en]`: row shows English (default, checked), app shows
    Simplified Chinese. Tapping English writes no override — English
    cannot be chosen from the row.
  - Choosing the non-default language does work (e.g. English under
    `[zh-Hans, …]` → app English).
- The row is absent when the system has a single preferred language
  (`[zh-Hant]`), so it would not reach single-language users anyway.
- Constraint for later: adding zh-Hans localized resources to the
  bundle (e.g. `InfoPlist.strings` for the Photos permission prompt,
  debt **420**) also makes iOS treat the app as multi-language, so the
  row and this conflict come back. Recorded as ADR-062: v1 ships no zh
  localized resources; reopening needs a new ADR and a device check.
