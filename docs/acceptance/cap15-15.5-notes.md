## Purpose

Record device sessions that inform Cap 15.5 memory work and Cap 15.8
narrative. Xcode Memory Report numbers here are **indicative readings**
(eye on a live curve / sticky High), not script-sampled, not replayable.
They support:

1. **One-shot qualitative triggers** (e.g. Round 3 vs Round 2: a jump
   anyone would call obviously wrong → start sized decode).
2. **Historical context** for why plan B exists.

They do **not** define a standing numeric gate (“must be ≤ N MB”,
“must not discernible-rise vs 261”). That class of gate is the same
unfalsifiable trap ADR-030 retired for Instruments hitch/hang bars —
Memory Report is a different tool with the **same** precision /
reproducibility limits in this product (Shuffle asset mix, Optimize
Storage locality, hand-logged peaks).

Cold-start `session_high` may be recorded for dual-track honesty but
**must not** soften or support any gapless / sized-decode verdict.

## Tooling Decision (execution detail for ADR-031 D11)

| Role | Tool | Rule |
|------|------|------|
| **Observation aid** | Xcode Debug Navigator **Memory Report** (indicative) | Use to notice **obvious** wrong-looking peaks, jetsam risk context, and plateau shape — **not** as a standing MB pass/fail bar |
| **Optional diagnosis** | Instruments Allocations | Allowed when a qualitative call is ambiguous; **not** a hard gate (ADR-030) |

**Scrubbing:** Memory Report timeline often cannot be scrubbed to a
precise `t0±2s` window. Do **not** require per-sample historical scrub.
Session `High` is sticky — screenshot after the sample window finishes.

### Round 3 trigger rule (historical — already fired)

Round 3’s hand-logged handoff peak sat in a **clearly wrong-looking**
band versus Round 2’s reading on the same protocol shape. That jump was
large enough for a **one-shot** ADR-031 D10 call (offset with
viewport-sized decode). That use of the numbers is allowed.

**Do not** promote Round 2’s ≈261 (or Round 3’s ≈354) into a standing
compare target for later rounds.

### Round 4 pass criteria (after sized decode) — qualitative only

No MB threshold. No “discernible vs 261”. No same-asset requirement.

1. **Peak character:** handoff windows no longer look like Round 3’s
   obviously-too-high spikes — owner judgement (“looks normal again”
   vs “still obviously wrong”). Exact MB is auxiliary, not the verdict.
2. **Hard fail signals (any one fails Round 4 memory):** jetsam,
   force-quit, or sustained climb without recovery during / after the
   three still handoffs.
3. **Visual side effect:** Fit interior must not look soft / under-decoded
   on Kafka after sized decode (qualitative; no resolution number match).

If the qualitative call is still uneasy, run another session for
confidence — to check the **judgement**, not to chase a numeric delta.
Same spirit as “borderline readings are weak evidence”: numbers assist;
they do not sentence.

If Round 4 still looks obviously heavy after that, **stop** and open a
new design (neighbour retain / ImageCache eviction, etc.). Do **not**
silently change Host still export in Cap 15.5.

**One-shot trigger (not a standing gate):** Round 3 handoff peaks sat in
an **obviously too-high** band relative to Round 2’s historical reading
(hand-logged ≈261 vs ≈354). Large enough that sample-id / iCloud timing
noise cannot rescue a “nothing wrong” story. Mechanism: gapless keeps the
prior frame while Layer 2 decodes — two decode footprints overlap; Layer 2
files are full original data, so unsized Flutter decode is expensive.

**Disposition:** visual goal of 15.5 gapless **met**. Memory path on
gapless-only **does not look acceptable**. **Next:** sized decode
(plan B) — `cacheWidth` / `cacheHeight` from **LayoutBuilder** constraints
× DPR, `.round()` — then Round 4 under the **qualitative** criteria above.

## Reading precision caveat (Round 2)

S1 (~219) and S2 (~243) were estimates; S3 (261) near-peak. Ascending
S1→S3 is **not** a proven law. Fine MB boundaries (e.g. “is 270 OK?”)
are not meaningful on this tooling.
