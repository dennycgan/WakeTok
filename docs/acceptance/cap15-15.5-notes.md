## Purpose

Record device sessions that inform Cap 15.5 memory work and Cap 15.8
narrative. Xcode Memory Report numbers here are **indicative readings**
(eye on a live curve / sticky High), not script-sampled, not replayable.
They support:

1. **One-shot qualitative triggers** (e.g. Round 3 vs Round 2: a jump
   anyone would call obviously wrong → start sized decode).
2. **Historical context** for why plan B exists / how Round 4 passed.

They do **not** define a standing numeric gate (“must be ≤ N MB”,
“must not discernible-rise vs 261”). That class of gate is the same
unfalsifiable trap ADR-030 retired for Instruments hitch/hang bars —
Memory Report is a different tool with the **same** precision /
reproducibility limits in this product (Shuffle asset mix, Optimize
Storage locality, hand-logged peaks).

Cold-start / sticky `session_high` may be recorded for dual-track honesty
but **must not** soften or support any gapless / sized-decode verdict.

## Tooling Decision (execution detail for ADR-031 D11)

| Role | Tool | Rule |
|------|------|------|
| **Observation aid** | Xcode Debug Navigator **Memory Report** (indicative) | Use to notice **obvious** wrong-looking peaks, jetsam risk context, and plateau shape — **not** as a standing MB pass/fail bar |
| **Optional diagnosis** | Instruments Allocations | Allowed when a qualitative call is ambiguous; **not** a hard gate (ADR-030) |

**Scrubbing:** Memory Report timeline often cannot be scrubbed to a
precise `t0±2s` window. Do **not** require per-sample historical scrub.
Session `High` is sticky — screenshot after the sample window finishes.

### Round 4 pass criteria (after sized decode) — qualitative only

No MB threshold. No “discernible vs 261”. No same-asset requirement.

1. **Peak character:** handoff windows no longer look like Round 3’s
   **systemic** obviously-too-high band (almost every sample elevated).
   An **isolated** tall spike with a concrete non–sized-decode cause
   (e.g. slow iCloud overlap) does not by itself reopen D10.
2. **Hard fail signals (any one fails Round 4 memory):** jetsam,
   force-quit, or sustained climb without recovery during / after the
   three still handoffs.
3. **Visual:** Fit interior not soft; **no stretch / fill-like aspect
   distortion** vs iOS Photos on the same asset (human compare — the
   acceptance method for the `exact`-policy bug). No blank/black flash
   on L1→L2.

If Round 4 still looks **systemically** heavy after that, **stop** and
open a new design (neighbour retain / ImageCache eviction, etc.). Do
**not** silently change Host still export in Cap 15.5.

**One-shot trigger (not a standing gate):** Round 3 handoff peaks sat in
an **obviously too-high systemic** band (almost every sample elevated)
relative to Round 2’s historical reading. Mechanism: gapless keeps the
prior frame while Layer 2 decodes — two decode footprints overlap; Layer 2
files are full original data, so unsized Flutter decode is expensive.

**Disposition:** visual goal of 15.5 gapless **met**. Memory path on
gapless-only **does not look acceptable**. Sized decode (plan B) required.

### Round 4a — **sized decode with `ResizeImagePolicy.exact` (FAIL visual)**

First plan B landing used `Image.file(cacheWidth:, cacheHeight:)`, which
wraps `ResizeImage` at **default `policy: exact`**. With both dimensions
set to the viewport box, decode targets that box’s aspect — **stretches**
non-matching stills (fill-like). Owner: blur→sharp briefly distorted vs
iOS Photos. **Visual FAIL.** Memory character already looked recovered
vs Round 3 (e.g. handoff peaks ~221 / 241 / 219 / 260, plateau ~201) but
Round 4 cannot pass on memory alone.

**Design note:** an earlier draft wrongly assumed “both cache dims ⇒
aspect-preserving fit like `BoxFit.contain`.” That describes
`ResizeImagePolicy.fit`, **not** the default `exact`.

#### S2≈334 attribution (write this way — not “owner shrugged”)

**Pattern contrast:** Round 3 = **systemic** high band on almost every
handoff (unsized decode under gapless). Round 4 = **isolated** tall
reading on S2 only; S1/S3 ~237 and plateau ~176 look ordinary.

**What the WT15 window supports for S2 (`B`):** Layer 2 was in a
multi-second `display_net` (iCloud / network transfer) while the UI
still held gapless prior pixels and the feed’s normal neighbour preview
/ display traffic could overlap in time. That stack raises peak RSS
during the wait.

**What sized decode does *not* control:** decode **target pixel box**
(viewport × DPR, `fit` policy). It does **not** remove network-transfer
buffers, gapless retention of the previous frame, or neighbour preheat
during a slow download. Those overlaps are **architecture that predates
plan B** (gapless + current-item Layer 2 fetch + ±1 preheat). A similar
isolated spike on a slow iCloud item could have appeared before
sized decode; it is **not** evidence that `ResizeImagePolicy.fit`
re-introduced Round 3’s systemic cost.

**Do not mis-cite:** `display_start supersede=true gen=2` at t≈8566 is
asset **`D` (S1)**, not S2/`B`. S2’s network window is **`B`** starting
~26204.

**Disposition:** no new Cap 15.5 fix for S2=334. Leave a breadcrumb so a
future isolated tall peak on a slow iCloud still is not re-blamed on
sized decode. If the same asset gets **repeated** `display_start` often
in daily use, watch at **15.8** / owner soak; open Known debt only if
frequent — not a new 15.5 workstream now.

**Also FYI (not a Round 4 fail):** repeated `display_start` on the same
id (D gen=2 supersede; later another `display_start` on B ~40104 while
the session continued) can **stack** with long iCloud waits and inflate
peaks. Related-to-but-not-same as Cap 15.4 preview supersede. Monitor at
15.8; no separate round now.
