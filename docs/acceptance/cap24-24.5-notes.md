## Locked test protocol — D4 (a)(b) must hit real PhotoKit resolve

Cap 7.6 (`14f28d7`) caches All / Photos / Videos resolve results for the
`ProviderContainer` process lifetime. **Same-process tab switch / re-enter
is a cache hit** — it does **not** re-run PhotoKit resolve and therefore
**must not** be used as the sole gate for ADR-050 Decision 4 (a)(b).

### Required trigger for (a) and (b)

| Step | Action |
|------|--------|
| Prep | Soft-delete (or restore) under test, then **force-quit** WakeTok so the process / `ProviderContainer` dies and the Browse Snapshot cache is gone. |
| Resolve | Relaunch → enter the **same** Pool / built-in tab. First Session build after relaunch must miss cache and call Host `resolveSource` / equivalent PhotoKit fetch. |
| Assert | See (a) / (b) below. |

Optional alternative (only if documented as equally cache-free): a path
known **not** to use Cap 7.6 process-lifetime Snapshot hits. Prefer
force-quit — it is unambiguous.

Do **not** PASS (a)/(b) on “switch tab away and back in the same process”
alone.

### Matrix rows (both devices: Kafka + i17)

| ID | Topic | Pass criteria |
|----|-------|----------------|
| D4-a | After App soft-delete, while asset remains in system Recently Deleted, a **fresh** Session resolve of the same Pool does **not** include that id | Force-quit → relaunch → enter Pool → id absent from Session Queue / feed |
| D4-b | After user **restores** the asset in Photos, a **later** fresh Session resolve **may** include it again | Restore in Photos → force-quit → relaunch → enter Pool → id may reappear |
| SYS | System second confirm after App confirm | Note if PhotoKit shows a second UI; accept stack (ADR-050 D3) — do not invent a third in-app confirm |
| CANCEL | User cancels system confirm | Host → `operationCancelled`; App **must not** show `cap24SoftDeleteFailed` (Q3 = A); Session Queue unchanged |
| FAIL | Host soft-delete failure (non-cancel) | Fail-closed: no Queue kick; `cap24SoftDeleteFailed` toast |
| SUCCESS | Host soft-delete success | Queue remove + advance (24.4); no revisit in this Session |

Run **D4-a** and **D4-b** once each on **Kafka** and **i17** (four resolve
checks minimum for the evidence pair).

## Accepted residual (not FAIL)

Same-process Snapshot **cache hit** after soft-delete (no force-quit) may
briefly rebuild a Session that still lists the deleted id (“ghost page”).
Cap 23 RD mapping → `unavailable` on probe / display paths. This is
**Accepted residual** under Q4′ = A — **not** a Cap 24 FAIL and **not**
grounds to add an ADR-048-style Snapshot invalidation hook in Cap 24.

If product later wants that closed, open a separate ADR with evidence —
out of Cap 24 default scope.

## Escape hatch (ADR-050 already locked)

If **D4-a fails under a real PhotoKit resolve** (defaults do **not**
exclude Recently Deleted from catalog/resolve fetches):

- Add a **Host-side explicit resolve filter** (e.g. fetch options /
  predicate) — ADR-050 Rejected alternatives escape.
- Do **not** invent a Dart Snapshot invalidation hook as the fix for this
  failure mode.
- No new ADR required to take the escape; record the filter land in
  24.5/24.6 notes + STATE/ADR Status as appropriate.
