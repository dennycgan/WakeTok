## Filed item (owner 2026-10-02)

owner proposed: show a center "!" while the finger stays down when a Live
long-press replay fails to load, with one neutral line of copy under it
(new dedicated key, states the result only, never a cause; announced once
to VoiceOver); fix/polish because, offline, a Live Photo
whose motion is only in iCloud fails the long-press replay and returns to
the still with no visible feedback (owner observation, iPhone 13 Pro,
2026-10-02) — the user acted and got no answer. The "!" shows only when
the failure arrives while the finger is still down; if the finger is
already up, nothing shows. A sync request error counts as a failure; a
cancel (swipe away, superseded request) does not. It hides at once on
release, page leave, app leaving the foreground, or pointer cancel.
Auto-play failure stays silent; no LIVE badge change, no text. Not
changed: the Share icon dims briefly during the failed attempt
(Share is disabled while the Live motion layer is mounted); no Console log
capture. Debt **436** reopened.

owner proposed: once the Cap 26 long-press has fired, follow only the
pointer that fired it (other pointers' down / move / up / cancel ignored)
and drop the 31.4a 10 s safety timeout; pre-fire behaviour unchanged;
fix/polish because Cap 26.5a release-to-stop is lost when a second finger
lands during the hold — the gesture resets without sending release, so
Live motion is not stopped on release, and with a Path S request in
flight playback can start after all fingers are up (code reading) —
against ADR-052 Cap 26.5a ("keep the same pointer session until pointer
up/cancel"; "do not wait for ready then stop"). Out of scope: before
fire, `_onMove` measures movement from any pointer against the last
pointer down's start position.

## Network back right after the failure (owner, 2026-10-02)

Observed: offline, auto-play of an iCloud-only Live failed; with the page
still current, the network was turned back on and the photo long-pressed.
The still stayed static and Share was not tappable after the long-press.
Swiping away and coming back showed the gold corner spinner, then the
Live played.

Code reading: the long-press runs the silent re-request (Path S, no
prepare chrome), which downloads the motion from iCloud
(`isNetworkAccessAllowed = true`); Share is disabled while the motion
layer is mounted; releasing during the request cancels it, which cancels
the PhotoKit download. Coming back runs auto-prepare, which shows the gold
spinner.

Not verified: whether holding through the download plays the Live;
whether Share returns on release. Not re-checked; the scenario is hard to
reproduce.

Not fixed (owner decision, edge case not worth new UI): debt **488**
Accepted (phase).
